# Этап 0 — инфраструктура: находки и грабли

Задачи 0.5–0.6, 14–19.09.2026.

## PostgreSQL 18: путь тома изменился

В образах 14–17 данные монтировались в `/var/lib/postgresql/data`. В 18 — в
`/var/lib/postgresql`. Со старым путём контейнер запускается и сразу умирает; причина написана
в `docker compose logs db` прямым текстом. Рецепты из статей до 2026 года здесь не работают.

## RustFS: документация расходится с образом

На этапе 0 хранилище объектов — RustFS `1.0.0` (тег появился на Docker Hub 16.09.2026, до этого
проект был в бете). Документация на момент внедрения противоречива, и проверка образа
дала другие ответы:

| Что               | Документация                                  | Образ (истина)                   |
| ----------------- | --------------------------------------------- | -------------------------------- |
| Порты             | страница Docker: 7000/7001; README: 9000/9001 | `9000/tcp`, `9001/tcp`           |
| Переменные ключей | две страницы дают два разных набора           | см. ниже                         |
| Путь данных       | `/data`                                       | `RUSTFS_VOLUMES=/data`           |
| Путь логов        | не описан                                     | `RUSTFS_OBS_LOG_DIRECTORY=/logs` |

Вывод на будущее: источник правды по этому образу — сам образ.

```bash
docker image inspect rustfs/rustfs:1.0.0 --format '{{json .Config.ExposedPorts}}{{"\n"}}{{json .Config.Env}}{{"\n"}}user={{.Config.User}}'
docker run --rm rustfs/rustfs:1.0.0 --help
```

## RustFS: имена переменных и MinIO-совместимость

Обёртка `/entrypoint.sh` при старте сама перечисляет, что понимает:

- основные: `RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY`
- из файла: `RUSTFS_ACCESS_KEY_FILE` / `RUSTFS_SECRET_KEY_FILE`
- псевдонимы: `RUSTFS_ROOT_USER` / `RUSTFS_ROOT_PASSWORD`
- совместимость с MinIO: `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`

Отсюда и расхождение в документации: наборов несколько, страницы описывают разные.
Используем основной.

Если ключи не заданы, RustFS откатывается на встроенные `rustfsadmin` / `rustfsadmin` и пишет
об этом `WARNING` в лог — то есть откат виден, но сервис при этом поднимается нормально.
Поэтому критерий приёмки — не «контейнер зелёный», а «в логах нет `WARNING` про ключи
и `rustfsadmin` в консоль не пускает».

## RustFS: права на тома

`/data` и `/logs` есть в образе и принадлежат `10001:10001` с правами `750`; процесс работает
под пользователем `rustfs`, не под root.

Отсюда выбор именованных томов вместо папки рядом с проектом. Именованный том при создании
наследует владельца и права с каталога, который уже есть в образе, — `chown` не нужен.
При монтировании хостовой папки права остались бы хостовыми (UID 501), процесс получил бы
`permission denied`, и потребовался бы `chown -R 10001:10001`, как и предлагает README RustFS.

## Для этапа 3

- **Секреты из файлов.** Переменные окружения видны в `docker inspect` и в списке процессов.
  В production перейти на `RUSTFS_ACCESS_KEY_FILE` / `RUSTFS_SECRET_KEY_FILE`.
- **CORS консоли.** В образ зашито `RUSTFS_CONSOLE_CORS_ALLOWED_ORIGINS=*`. В dev безвредно —
  порт привязан к `127.0.0.1`. В production консоль наружу не публикуется вообще; пункт
  чек-листа безопасности PRD §8.

## `docker compose config` печатает секреты

Команда раскрывает все подстановки и выводит итоговую конфигурацию, включая значения
`POSTGRES_PASSWORD` и `RUSTFS_SECRET_KEY` открытым текстом. Для проверки файла использовать
`docker compose config --quiet`: тот же разбор и та же валидация, но без вывода — судим
по коду возврата.

Полный вывод `config` уместен только когда нужно посмотреть, во что раскрылась конфигурация,
и тогда его никуда не копируют. Секрет, попавший в историю терминала, в чат или в тикет,
считается скомпрометированным и меняется.

## macOS: занятые порты

5432 обычно держит нативный PostgreSQL из Homebrew, 7000 — процесс `ControlCenter`
(AirPlay Receiver) на всех интерфейсах. Проверять до правки compose:
`lsof -nP -iTCP:<порт> -sTCP:LISTEN`.

## Общий урок

Все четыре ошибки этапа сводились к одному: успешный старт и зелёная проверка не доказывают,
что настройка применилась. `pg_isready` был зелёным при нерабочем пользователе; RustFS
поднимается на публичных ключах; healthcheck хранилища подтверждает только HTTP-ответ.
Проверять надо то, что должно сломаться.
