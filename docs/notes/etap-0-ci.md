# Этап 0 — CI: что сделал и почему

Задача 0.11, 25.09.2026. Файл проверки писал Никита сам (правило «руками»), агент объяснял и проверял.

## Что появилось

`.github/workflows/ci.yml` — одна задача `check` на `ubuntu-latest`: забрать код, поставить pnpm, поставить Node с кэшем pnpm, `pnpm install --frozen-lockfile`, затем `lint`, `format:check`, `typecheck`, `test`, `build`. Запускается на pull request в `master` и на push в `master`, полный прогон — около 40 секунд.

На GitHub — набор правил `master` для основной ветки: изменения только через pull request, проверка `check` обязательна, force push и удаление ветки запрещены. Слияние — squash.

## Решения

**Два триггера.** На pull request проверяется ветка до слияния — точнее, результат её слияния с текущим `master`. На push в `master` — то, что на самом деле попало в основную ветку. Второй запуск ещё и сохраняет кэш pnpm для `master`: кэш из запуска на pull request виден только этому pull request'у, кэш `master` — всем следующим. Push в остальные ветки проверку не запускает: она начинается, когда открыт pull request, и дальше идёт на каждый push в его ветку.

**Версии — из репозитория, а не из файла проверки.** `pnpm/action-setup` без параметра `version` читает поле `packageManager` в корневом `package.json`, `setup-node` — файл `.nvmrc`. Локально и в CI одни и те же pnpm и Node, меняются в одном месте.

**pnpm ставится раньше Node.** `setup-node` с `cache: pnpm` спрашивает у pnpm, где лежит хранилище пакетов, — без установленного pnpm этот шаг падает.

**`--frozen-lockfile`.** Если `pnpm-lock.yaml` не совпадает с `package.json`, установка падает, а не обновляет файл молча. В CI pnpm включает этот режим и сам; флаг записан явно, чтобы это было видно из файла.

**Минимум прав.** `permissions: contents: read` — токен задачи может только читать репозиторий: если готовый шаг из чужого репозитория (`uses:`) окажется вредоносным, запушить он ничего не сможет. `persist-credentials: false` — `checkout` не оставляет токен в `.git/config` для следующих шагов. Секретов в CI нет: unit-тестам не нужны ни база, ни хранилище.

**Правило без исключений.** Список обхода пуст, поэтому прямой push в `master` отклоняется даже у владельца — с ошибкой `GH013`. Required approvals — 0: одобрить свой pull request нельзя, и с 1 разработчик-одиночка заблокировал бы сам себя. «Require branches to be up to date» не включено: параллельных веток почти не бывает, а то, что попало в `master`, всё равно проверяет запуск по push.

**Squash.** Одна ветка — один коммит в `master` с заголовком pull request'а. История читается как список изменений, промежуточные коммиты — в том числе агентские — в неё не попадают. Поэтому заголовок pull request'а пишется по Conventional Commits.

**Сборка образов — на этап 3.** В исходной формулировке задачи была сборка Docker-образов, но `Dockerfile` появятся только вместе с production-контуром. Вместо неё в CI — сборка пакетов и проверка форматирования.

## Порядок работы с этого момента

1. Ветка от свежего `master`, имя по типу коммита — `feat/…`, `fix/…`, `docs/…`, `ci/…`, `chore/…`: например, `git switch -c docs/ci-note`.
2. Коммиты, затем `git push -u origin <ветка>`; ссылку на создание pull request GitHub отдаёт в ответ на push.
3. Pull request с коротким «что и почему», зелёная `check`, Squash and merge.
4. Локально: `git switch master`, `git pull --prune`, `git branch -D <ветка>`. Большая `-D` — потому что после squash в `master` лежит новый коммит, и git считает ветку неслитой, хотя её содержимое уже там.

## Грабли

- **Ревью черновика нашло четыре вещи.** Имя `Deploy` у проверки, которая ничего не выкатывает, — стало `CI`. Событие `pull-request` через дефис — GitHub знает только `pull_request`. Параметры `setup-node` были записаны флагами, как у консольной команды, — готовому шагу они передаются блоком `with:`. Пробелы в конце строк — Prettier проверяет и YAML, так что шаг «форматирование» уронил бы сам `ci.yml`.
- **VS Code прячет ссылку на pull request.** Кнопка «Sync Changes» не показывает ответ GitHub на push. Открыть — по плашке «Compare & pull request» на странице репозитория или по адресу `…/pull/new/<ветка>`.
- **Push в ветку без pull request ничего не запускает.** Первое, что смотреть на вопрос «почему нет запуска», — условия в `on:`.
- **Обязательная проверка привязана к имени.** Правило ждёт проверку `check` — это ключ задачи в `jobs:`. Переименовать задачу без правки правила — заблокировать все слияния: GitHub будет ждать проверку со старым именем.
