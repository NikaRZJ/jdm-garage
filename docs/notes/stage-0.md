# Этап 0 — каркас: что сделано и почему

14.09–08.10.2026, 16 задач. Подробности — в заметках `etap-0-*.md` и ADR 001–004.

За этап собран каркас, на котором дальше строится витрина: монорепозиторий на pnpm workspaces с общими zod-схемами для API и фронта; локальная среда в Docker Compose — PostgreSQL 18 с pgvector и S3-совместимое хранилище RustFS; скелет API на NestJS 12 в нативном ESM с проверками `/api/health` и `/api/ready`; Drizzle и первая миграция; скелет фронта на React 19, Vite 8, TanStack Router и Query, MUI 9. Каждый pull request проходит CI на GitHub Actions — линт, формат, типы, тесты, сборка, около 40 секунд, — а попасть в `master` можно только через pull request с зелёной проверкой. Плюс эскизы трёх ключевых экранов и `CLAUDE.md` со скиллами для агента.

Четыре решения с альтернативами записаны в ADR. Монорепозиторий — ради атомарных изменений контракта: правка схемы в `packages/shared` сразу показывает, что сломалось в обоих приложениях. Drizzle, а не Prisma, — потому что миграция остаётся SQL-файлом, а построитель запросов читается как SQL: учебная цель — понимать запросы, индексы и планы, а не прятаться от них. RustFS — вместо MinIO, чей репозиторий в архиве, и Garage с лицензией AGPL. Для входа — JWT access на 15 минут и refresh в httpOnly cookie с ротацией и семьями токенов; в ADR честно записано, что при одном origin серверные сессии были бы проще и не хуже, а выбор сделан ради учебной цели — подписи, ротации и защиты от CSRF.

Труднее всего оказалось не написать код, а убедиться, что настройка действительно применилась. Документация RustFS называла одни порты и переменные, а образ — другие; `drizzle-kit` без явного `ssl: false` включал шифрование и обрывал соединение на рукопожатии — причина нашлась только в исходнике; у PostgreSQL 18 сменился путь тома. Зелёный `pg_isready` при нерабочем пользователе и RustFS, который спокойно стартует на встроенных ключах, дали главный вывод этапа: проверять надо то, что должно сломаться, а источник правды — образ и исходник, а не пересказ.

Работа идёт в паре с ИИ-агентом, и правила этой пары — тоже результат этапа. Схему базы, авторизацию, поиск, nginx и CI пишет разработчик; шаблонный код, тесты по образцу и тексты документов — агент; решения в ADR принимает человек, текст записывает агент; коммит и PR — только после явного «да», сливает только человек. Уроки сессий становятся правилами `CLAUDE.md`: незнакомый термин сначала объяснить, потом спрашивать; версии пакетов брать старше суток; секреты не печатать. Проверка этих правил в Claude Code заодно нашла четыре непрописанные границы и два противоречия в модели данных PRD — их предстоит решить перед схемой каталога.

Этап планировался на две недели и около 8 часов, а занял три с лишним недели. Сильнее всего разошёлся с оценкой разбор авторизации: около двух часов вместо получаса — понять механику JWT, ротации и CSRF с нуля оказалось дольше, чем записать решение, и это ожидаемая цена учебного проекта. Дальше — этап 1: схема справочника и машин, сид и генератор 10 000 машин, API каталога с фильтрами, интеграционные тесты на настоящем PostgreSQL, страницы каталога по эскизам и отчёт по планам запросов.
