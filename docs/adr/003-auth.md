# ADR-003. JWT access + refresh с ротацией против серверных сессий

- Статус: принято
- Дата: 07.10.2026
- Решение обсуждено с разработчиком, текст записан агентом по итогам обсуждения

## Контекст

API нужна аутентификация для четырёх ролей (PRD §4.3): регистрация и вход по email и паролю, проверка прав на каждом запросе, выход, блокировка пользователя администратором. Требования к безопасности — PRD §8: пароли argon2id, ни `password_hash`, ни `token_hash` в ответах, CSRF-защита, лимиты частоты. PRD §4.3 уже описывает схему на JWT access + refresh и просит записать ADR: почему она, а не серверные сессии, и какие компромиссы приняты. Это задача 0.13.

Условия. Фронт — SPA на React, API — NestJS; в dev и production они на одном origin: API под `/api`, в dev — через прокси Vite, в production — через nginx (этап 3). Масштаб — десяток менеджеров и сотни покупателей, нагрузка на базу не аргумент. Учебная цель У2 (PRD §1.2) — «аутентификация, роли, безопасность»: JWT и refresh в httpOnly cookie с ротацией, RBAC, CSP, лимиты; в контексте проекта уточнено — «закрывает и токены, и cookies, частая тема собеседований». Бюджет — около 4 часов в неделю; этап 2 (auth, заявки, админка) оценён в ~16 часов. Токены выдаются и проверяются своим кодом на `jose`, без готовых стратегий Passport (PRD §4.3, `CLAUDE.md`): цель учебная.

## Варианты

**Вариант А. Серверные сессии.** После входа сервер пишет строку в таблицу сессий и отдаёт браузеру только её id в httpOnly cookie; на каждом запросе — поиск по таблице. Сильные стороны: одна сущность; отзыв мгновенный — удалили строку, и следующий запрос получит 401; клиент не хранит ничего, cookie идёт сама; заметно меньше кода. Это выбор по умолчанию в классических веб-фреймворках (Django, Rails, Laravel, Spring Security, `express-session`), и для одиночного SPA с собственным API он не хуже варианта Б по безопасности. Свежая рекомендация IETF для браузерных приложений (RFC 10017, август 2026) тоже советует не отдавать токены в браузер, а держать их на бэкенде с cookie-сессией (схема BFF). Цена: cookie идёт с каждым запросом, поэтому CSRF-защита нужна на всех изменяющих эндпоинтах; поход в базу на каждый запрос — при нашем масштабе незаметно. Отклонён по главному критерию: учит сессии и CSRF, но не токены, подпись, ротацию и семьи.

**Вариант Б. JWT access + refresh с ротацией.** Access — JWT на 15 минут, хранится в памяти вкладки и идёт в заголовке `Authorization`; проверяется подписью, без базы. Refresh — случайная строка на 30 дней в cookie `HttpOnly; Secure; SameSite=Lax; Path=/api/auth`; в базе — хэш; при каждом обмене выдаётся новая пара, старый refresh помечается отозванным; повторное использование отозванного refresh — признак кражи, отзывается вся семья токенов. Это схема мира OAuth 2.0: ротация refresh с обнаружением повторного использования — требование RFC 9700 (январь 2025) для публичных клиентов; так устроены Auth0 и Keycloak. По сути вариант Б включает вариант А: refresh — это и есть серверная сессия (строка в таблице, поиск, мгновенный отзыв), а сверх неё — подпись и проверка JWT, ротация как транзакция, таблица токенов с семьями, клиентский перехватчик 401. Цена: отзыв access не мгновенный; две сущности; CSRF-защита refresh и выхода; больше кода и тестов — ориентировочно на 2–3 часа больше, чем А.

**Вариант В. Только JWT с долгим сроком.** Без refresh и без таблицы: access на дни или недели. Проще обоих, но отозвать токен нельзя вовсе — блокировка пользователя не действует до истечения срока. Отклонён: нарушает требование PRD §4.4 «заблокированный пользователь теряет действующие сессии в течение ≤ 15 минут».

## Решение

JWT access + refresh с ротацией (вариант Б) — ради учебной цели У2, а не потому, что этой архитектуре он нужен: сессии были бы проще и не хуже. Б покрывает всё, чему учит А, и добавляет подпись, ротацию, семьи токенов и клиентскую часть; схема повторяет RFC 9700, поэтому навык переносится на мир OAuth, а пара «сессии против JWT» — самый частый вопрос на понимание auth на собеседованиях.

Параметры (PRD §4.3, §6.2, §8):

- access: JWT, 15 минут, только в памяти вкладки, заголовок `Authorization: Bearer`; в payload — `sub` и `role`; роли также в базе;
- refresh: случайная строка, 30 дней, cookie `HttpOnly; Secure; SameSite=Lax; Path=/api/auth`; в базе `refresh_tokens` — хэш (`token_hash`), `family_id`, `expires_at`, `revoked_at`, `replaced_by_id`;
- обмен: `POST /api/auth/refresh` выдаёт новую пару и отзывает старый refresh — пометка `revoked_at`, не удаление, иначе повтор не заметить; повтор отозванного refresh отзывает семью; обмен — в транзакции, чтобы два одновременных refresh с одним токеном не выдали две пары;
- выход отзывает текущий refresh; «выйти на всех устройствах» — все семьи пользователя; блокировка — все семьи, плюс проверка `is_blocked` при входе и при обмене;
- CSRF на refresh и выходе — три слоя: `SameSite=Lax`; проверка `Origin`/`Sec-Fetch-Site` (ожидаем same-origin); обязательный заголовок `X-Requested-With`, который HTML-форма поставить не может, а `fetch` с чужого origin не пройдёт preflight. CORS в API не включается: фронт и API на одном origin, а `app.enableCors()` с произвольным origin и `credentials` снимает третий слой одной строкой;
- пароли — argon2id; реализация — `jose` и `argon2`, без Passport-стратегий;
- фронт при 401 один раз вызывает refresh и повторяет запрос; при неудаче — страница входа с возвратом на исходную.

Не решено здесь, решается при реализации на этапе 2: алгоритм подписи (HMAC на секрете или асимметричная пара ключей) и ротация ключа через `kid` в заголовке токена (PRD §8).

Точка пересмотра: если фронт и API окажутся на разных origin или появится внешний провайдер входа (OAuth, «войти через …»), вернуться к схеме BFF по RFC 10017 — токены остаются на бэкенде, браузеру — cookie-сессия. Плановая проверка — старт этапа 4, «дозревание auth».

## Последствия

Хорошее: учебная цель У2 отрабатывается целиком — подпись, ротация, семьи, cookie, CSRF, плюс транзакция на ротации (У1); проверка access не ходит в базу; CSRF-поверхность — два эндпоинта под `/api/auth` вместо всего API; схема соответствует RFC 9700.

Плохое, с которым придётся жить:

- **Отзыв не мгновенный.** После блокировки или смены роли старый access работает до `exp`, то есть до 15 минут: подпись сходится, а в базу проверка не ходит. Смягчение: короткий срок access; при обмене refresh проверяются `is_blocked` и актуальная роль, поэтому новая пара заблокированному не выдаётся; блокировка отзывает все семьи. В PRD §4.3 зафиксировано как допустимое.
- **CSRF на refresh и выходе.** Cookie идёт с любого сайта, поэтому чужая страница может вызвать refresh. Токенов она не получит — ответ ей не виден, — но ротация сработает, браузер пользователя останется со старым refresh, и следующий обмен будет выглядеть как кража: семья отозвана, пользователь выкинут, в базе ложная тревога. Смягчение — три слоя защиты выше; `SameSite=Lax` — дополнительный слой, не единственный.
- **Две сущности и больше кода.** Таблица токенов, ротация, семьи, перехватчик на фронте, тесты на ротацию, повтор и гонку. Смягчение: обвязку — DTO, скелет модуля, тесты по образцу — пишет агент, ядро — разработчик (`CLAUDE.md`, правило 1).
- **Семья отзывается одна.** При краже с одного устройства другие сессии пользователя живут — намеренно, чтобы не выкидывать его отовсюду; если украдено с двух устройств, вторая семья выживет. Лекарство — «выйти на всех устройствах».
- **Токены в браузере.** Access лежит в памяти вкладки, и чужой скрипт на странице может прочитать его на оставшиеся до 15 минут; RFC 10017 для SPA советует BFF без токенов в браузере. Смягчение: короткий срок, CSP без inline-скриптов (PRD §8), refresh — в httpOnly cookie. Точка пересмотра — выше.
