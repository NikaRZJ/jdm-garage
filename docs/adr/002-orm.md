# ADR-002. Drizzle против Prisma, Kysely и чистого SQL

- Статус: принято
- Дата: 21.09.2026
- Решение обсуждено с разработчиком, текст записан агентом по итогам обсуждения

## Контекст

API нужен слой доступа к PostgreSQL 18 с pgvector. Главная учебная цель проекта в этой части — понимать SQL, индексы и планы запросов, а не спрятаться от них. Схему базы и миграции разработчик пишет сам (правило «руками»), поэтому инструмент должен оставлять SQL видимым: и в запросах, и в миграциях.

Остальные ограничения: TypeScript strict и нативный ESM во всём монорепозитории; интеграционные тесты на реальном PostgreSQL через Testcontainers; драйвер уже выбран 19.09 — `pg` (node-postgres), пул создаётся в `apps/api` и раздаётся под токеном `PG_POOL`.

## Варианты

**Чистый SQL через `pg`.** Лучше всего учит SQL — между разработчиком и базой ничего нет. Цена: типы результатов пишутся руками и расходятся со схемой при каждой правке, инструмента миграций нет — его пришлось бы выбирать отдельно, а изменения схемы описывать без проверки. Для объёма проекта это много шаблонного кода, который ничему не учит.

**Prisma.** Самый быстрый старт: схема в своём формате, клиент генерируется, миграции тоже. Отклонён по главному критерию — Prisma намеренно скрывает SQL за собственным языком запросов, и понимание индексов и планов пришлось бы добывать в обход инструмента. Плюс отдельный движок запросов и шаг генерации клиента, который усложняет монорепозиторий.

**Kysely.** Типизированный построитель запросов, очень близкий к SQL. Отклонён из-за миграций: схема не описывается как источник правды, и сгенерировать миграцию из изменения схемы нельзя — нет аналога `drizzle-kit generate`. Каждую миграцию пришлось бы писать целиком руками, без сверки со схемой.

**Drizzle.** Схема описывается на TypeScript, запросы — построитель, который читается почти как SQL, типы результатов выводятся из схемы. `drizzle-kit` сравнивает схему с предыдущим снимком и генерирует миграцию обычным SQL-файлом, который можно и нужно прочитать до коммита. Сырой SQL доступен через шаблонный тег `sql` с параметрами.

Внутри Drizzle — второй выбор, линия версий. **Stable `0.45.2`** (27.03.2026) проверена в нашем ESM-окружении и описана в подавляющем большинстве статей и ответов, но заморожена: полгода без релизов, исправления идут только в v1. **`1.0.0-rc.4`** (июнь 2026) — будущий API: новое описание связей (`defineRelations` вместо `relations`), новый формат папки миграций и таблицы миграций, zod-интеграция в самом пакете. Но это предрелиз, а примеры в интернете в основном написаны под v0.

## Решение

Drizzle ORM `0.45.2` и drizzle-kit `0.31.10`, версии зафиксированы точно. Драйвер — `pg`; Drizzle оборачивает тот же пул, что лежит под `PG_POOL`, второе подключение к базе не заводится. Объект Drizzle раздаётся сервисам под собственным токеном: его тип — псевдоним, а не класс, и ключом внедрения зависимостей он служить не может.

Главная причина выбора Drizzle — он оставляет SQL видимым там, где это важно для учёбы: сгенерированная миграция — это SQL-файл, а построитель запросов повторяет структуру SQL. Причина выбора линии 0.45 — для первого знакомства с миграциями и схемой важнее всего находить ответы, когда застрял, а они почти все написаны под эту линию.

**Точка пересмотра — старт этапа 3, до первого выката в production.** Если к этому моменту вышел стабильный Drizzle 1.0 с официальной инструкцией перехода — переезжаем до выката. Если нет — остаёмся на 0.45 и фиксируем это отдельной строкой в ADR.

## Последствия

Хорошее: схема — TypeScript-код в репозитории, миграции — SQL-файлы, которые проходят ревью; типы запросов выводятся из схемы, расхождение ловит компилятор; сырой SQL под рукой, когда построителя не хватает.

Плохое, с которым придётся жить:

- **Замороженная линия.** Ошибку, найденную в 0.45, никто не исправит. Если упрёмся — обходим сырым SQL или ускоряем переход на v1.
- **Переезд на v1 не бесплатный.** Придётся переписать описания связей и перевести папку миграций на новый формат. Самая дорогая часть — смена формата таблицы миграций в уже работающей базе, поэтому переезд делается до production, пока dev-базу можно пересоздать. Связей к этапу 3 будет порядка десятка — это вечер работы, а не проект.
- **Сгенерированную миграцию обязательно читать.** `drizzle-kit` генерирует SQL по разнице снимков и может выбрать не то действие — например, удалить и создать колонку вместо переименования. Правило: каждая сгенерированная миграция читается как SQL до коммита, без исключений.
- **Секрет базы живёт в одном месте.** Конфигурация `drizzle-kit` собирает подключение из тех же `POSTGRES_*`, что и API; отдельной строки подключения с паролем в `.env` не появляется.
