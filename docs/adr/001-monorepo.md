# ADR-001. Монорепозиторий против двух репозиториев

- Статус: принято
- Дата: 16.09.2026
- Решение обсуждено с разработчиком, текст записан агентом по итогам обсуждения

## Контекст

Проект делает один разработчик в опциональных вечерних слотах, ориентир — 3–4 часа в неделю. Кода два приложения: API на NestJS (`apps/api`) и SPA на React (`apps/web`). Между ними общий контракт: zod-схемы фильтров, DTO и перечислений в `packages/shared` и спецификация OpenAPI, которую производит API и из которой генерируется типизированный клиент для фронта. Настройки TypeScript, ESLint и Prettier тоже одни на всех. Репозиторий публичный и служит портфолио.

## Варианты

**Монорепозиторий на pnpm workspaces.** Все пакеты в одном репозитории и ссылаются друг на друга по имени через `workspace:*`; pnpm кладёт в `node_modules` символические ссылки на соседние папки, и для Node и TypeScript такой пакет неотличим от установленного из реестра. Изменение контракта — один коммит и один прогон CI. Цена — связанность, см. последствия.

**Два репозитория.** API и фронт живут отдельно. Изменение общей схемы — это опубликовать пакет в реестр, поднять версию и обновить её в двух местах: три PR вместо одного и окно, в котором фронт и бэк рассогласованы. Спецификацию OpenAPI нужно где-то хранить и версионировать. Для одного разработчика вся эта церемония — накладные расходы без выгоды.

**Два репозитория плюс общий пакет в реестре.** То же самое, но общий код формализован как npm-пакет. Даёт независимые релизы, которые здесь не нужны, и добавляет версионирование пакета к каждому изменению схемы.

## Решение

Монорепозиторий на pnpm workspaces: `apps/api`, `apps/web`, `packages/shared`, `packages/config`, `infra/`, `docs/`. Главная причина — атомарные изменения контракта: правка zod-схемы в `packages/shared` в том же коммите показывает, что сломалось в обоих приложениях, и чинится одним PR. Для одного разработчика это единственный вариант без лишней церемонии.

## Последствия

Хорошее: один коммит на изменение контракта; одна команда для генерации клиента из OpenAPI; один набор настроек линтера и TypeScript в `packages/config`; одна точка отката.

Плохое, с которым придётся жить:

- CI гоняет всё на каждый PR; когда станет долго — фильтрация по изменённым пакетам.
- Деплой по тегу выкатывает оба приложения, независимых релизов нет.
- Фантомные зависимости: резолвинг модулей в Node поднимается до корня репозитория, поэтому пакет может работать за счёт зависимости, объявленной в корневом `package.json`, а не в своём. pnpm защищает от этого внутри пакетов (плоского `node_modules` нет — реальные пакеты лежат в `.pnpm`), но не от подъёма до корня. Правило: каждый пакет объявляет всё, что импортирует, даже если «и так работает».
- Сборка Docker-образа одного приложения на этапе 3: контекст сборки — весь репозиторий, просто скопировать `apps/api` нельзя; использовать `pnpm deploy --filter`.
