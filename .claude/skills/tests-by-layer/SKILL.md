# Тесты по слоям

Задача не готова, пока тесты не зелёные локально (`pnpm test`) и в CI. Каждый слой проверяет своё — одно и то же поведение на двух слоях не дублируй.

## Какой слой выбрать

- **Логика без ввода-вывода** — чистая функция, zod-схема, сервис Nest с подменёнными зависимостями → unit.
- **Компонент или страница фронта** → тест компонента, сервер подменяет MSW.
- **Эндпоинт API, SQL, миграция, транзакция** → интеграционный тест на настоящем PostgreSQL. Моки базы здесь запрещены: они проверяют мок, а не запрос.
- **Сценарий пользователя через весь стек** → e2e, только для ключевых сценариев.

## Unit — Vitest

- Файл рядом с кодом: `*.spec.ts` в `apps/api`, `*.test.ts(x)` в `apps/web`.
- Зависимости сервиса Nest подменяются через `Test.createTestingModule` и `useValue` — включая базу: так проверяется логика сервиса, а не SQL.
- Время и случайность фиксируются: `vi.useFakeTimers()`, значения передаются параметром.
- Образцы: `apps/api/src/health/health.service.spec.ts`, `apps/api/src/database/database.module.spec.ts`.

## Компоненты фронта — Testing Library и MSW

- Сервер подменяет MSW: обработчики по умолчанию — `apps/web/src/test/server.ts`, подключение — `apps/web/src/test/setup.ts`. Запрос без обработчика — ошибка теста (`onUnhandledRequest: 'error'`).
- Ответ для конкретного теста — `server.use(http.get(...))` внутри теста; после каждого теста обработчики сбрасываются к умолчанию сами.
- Свой `QueryClient` на каждый тест, с `retry: false` — иначе ошибка покажется только после трёх повторов.
- Ищи элементы так, как их видит пользователь: `findByRole`, `getByText`. Не по классам и не по `data-testid`, если есть роль или текст.
- Покрывай состояния: загрузка, пусто, ошибка, данные. Отдельный случай — ответ сервера, не прошедший схему zod: для пользователя это ошибка, и тест на это нужен.
- Образец — `apps/web/src/components/api-status.test.tsx`.

## Интеграционные тесты API — с задачи 1.8

- `@nestjs/testing` + supertest + Testcontainers с тем же образом, что в `compose.yaml` (`pgvector/pgvector:0.8.6-pg18-trixie`). Перед тестами применяются миграции.
- Покрытие для списков: каждый фильтр отдельно, комбинация, пагинация, сортировка, невидимость непубличных статусов списком и по прямой ссылке, ошибки 404 и 422.
- Первый тест пишется вместе с разработчиком, дальше — по образцу.
- В CI Docker на `ubuntu-latest` есть; переменные окружения для тестов — блок `env:` в workflow с тестовыми значениями, это не секреты.
- Команда `pnpm test:int` появится вместе с первым тестом.

## E2e — Playwright, с задачи 1.10

- Только сценарии, которые нельзя сломать: каталог → фильтр → карточка → страница модели. Граничные случаи — на нижних слоях.

## Общие правила

- Проверяй поведение через публичный интерфейс, а не внутреннее устройство.
- Названия тестов — по-русски, как поведение: `it('/ready отвечает 503, когда зависимость недоступна')`.
- Нашёл ошибку — сначала падающий тест, который её воспроизводит, потом исправление.
- Не ослабляй проверку, чтобы тест позеленел. Если неправ тест, а не код, — скажи об этом.
- Прогон: `pnpm test`, по пакету — `pnpm --filter @jdm/api test`, `pnpm --filter @jdm/web test`.
