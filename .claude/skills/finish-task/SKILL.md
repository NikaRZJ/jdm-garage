# Закрытие задачи

Задача закрыта, когда код попал в `master` через pull request с зелёной проверкой `check`, тесты по слоям на месте, есть заметка «что сделал и почему», а решения с альтернативами записаны в ADR. Иди по шагам и в конце покажи разработчику короткий итог: что прошло, что нет.

## 1. Тесты

Новое поведение покрыто на своём слое — см. скилл `/tests-by-layer`. Нет теста — напиши или объясни разработчику, почему его нет. Сначала тесты, потом проверки: иначе проверки придётся гонять дважды.

## 2. Проверки — как в CI

```sh
pnpm lint && pnpm format:check && pnpm typecheck && pnpm test && pnpm build
```

Упал формат — `pnpm format` и повтор. Красное не коммитится.

## 3. Безопасность — если задача трогает auth, файлы, SQL или LLM

- пароли — argon2id; access-токен — в памяти, refresh — в httpOnly-cookie с ротацией и семьями токенов;
- refresh защищён от CSRF: `Origin`/`Sec-Fetch-Site` и собственный заголовок;
- в ответах нет `password_hash` и `token_hash`;
- SQL только параметризованный;
- тип файла — по содержимому, изображения перекодируются;
- текст пользователя в промпте — только как данные;
- секретов нет в коде, логах и выводе команд.

Полный чек-лист — PRD §8.

## 4. ADR

В задаче выбирали между вариантами? Если да, а ADR нет — предложи записать (скилл `/adr`).

## 5. Заметка «что сделал и почему»

Файл `docs/notes/etap-<N>-<тема>.md`, по-русски. Образец — `docs/notes/etap-0-ci.md`.

```markdown
# Этап N — <тема>: что сделал и почему

Задача N.M, ДД.ММ.ГГГГ. Кто делал: разработчик (правило «руками»), агент или вместе.

## Что появилось

## Решения

## Грабли

## Проверено

## Отложено
```

- **Решения** — почему так, а не иначе; альтернативы — одной фразой.
- **Грабли** — только реальные, с выводом, как не наступить снова.
- **Проверено** — чем именно: команды и результаты, а не «вроде работает».

Заодно документация рядом: изменились команды, порты или порядок запуска — поправь README; изменились правила или команды для агента — `CLAUDE.md`.

## 6. Коммит и pull request

- Ветка `<тип>/<тема>` от свежего `master`; если работа шла в `master` — создай ветку до коммита.
- Коммит по Conventional Commits, текст после префикса — по-русски: `docs: заметка по задаче 0.11 — CI и правило для master`.
- Заголовок PR совпадает с сообщением коммита: при squash он становится коммитом в `master`.
- Описание PR — две-четыре строки: «Что», «Зачем», «Не вошло».
- Коммит, push и PR — только после явного «да» разработчика. Сначала покажи команды и тексты.
- Сливает PR только разработчик. Авто-слияние не предлагай и не включай.

## 7. После слияния

```sh
git switch master
git pull --prune
git branch -D <ветка>
```

`-D` — потому что после squash git считает ветку неслитой. Напомни разработчику отметить задачу в плане — он лежит в папке документов, вне репозитория.
