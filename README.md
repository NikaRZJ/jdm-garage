# jdm-garage

Сайт-витрина импортёра JDM-автомобилей с админкой и поиском на естественном языке.
Учебный пет-проект: цель — отработать бэкенд на NestJS + PostgreSQL, аутентификацию и роли,
production-контур и одну LLM-фичу в production.

Правила работы над проектом — `CLAUDE.md`, архитектурные решения — `docs/adr/`,
заметки по этапам — `docs/notes/`, требования и этапы — PRD в папке документов (вне репозитория).

## Требования

- **Node 24 LTS** — версия зафиксирована в `.nvmrc`
- **pnpm 12** — `npm i -g pnpm`
- **Docker** с Compose v2; на macOS это Docker Desktop, и он должен быть запущен
- **OpenSSL** — для генерации секретов, есть в macOS из коробки

## Запуск за 5 минут

### 1. Зависимости

```bash
nvm use
pnpm install
```

### 2. Переменные окружения

```bash
cp .env.example .env
openssl rand -hex 24
```

Открой `.env` и заполни два пустых значения:

- `POSTGRES_PASSWORD` — пароль базы
- `RUSTFS_SECRET_KEY` — секретный ключ хранилища, подставь вывод `openssl rand -hex 24`

Оба значения — секреты. `.env` не коммитится; в репозитории лежит только `.env.example`
с именами переменных и несекретными значениями.

Секреты генерируй именно в hex: в base64 попадают символы, которые Docker Compose
принимает за синтаксис подстановки переменных.

### 3. Инфраструктура

```bash
docker compose config --quiet
docker compose up -d
docker compose ps
```

`docker compose config --quiet` проверяет файл и раскрытие переменных, ничего не печатая:
код возврата 0 — всё в порядке. Запускать до `up`, чтобы ошибка в переменных всплыла сразу,
а не в логах упавшего контейнера.

Флаг `--quiet` здесь обязателен. Без него команда печатает итоговую конфигурацию **вместе
с раскрытыми значениями секретов** — пароль базы и ключ хранилища окажутся на экране,
в истории терминала и везде, куда этот вывод скопируют.

Оба сервиса должны дойти до состояния `healthy` — это занимает 10–20 секунд.

### 4. Проверка

База — расширение `pgvector` на месте:

```bash
docker compose exec db psql -U jdm -d jdm_garage -c "select extname, extversion from pg_extension where extname = 'vector'"
```

Хранилище — ключи из `.env` применились:

```bash
docker compose logs storage | grep -i warning
```

Вывод должен быть **пустым**. Если в логах есть предупреждения про `RUSTFS_ACCESS_KEY` или
`RUSTFS_SECRET_KEY` — переменные не подхватились, и RustFS поднялся на встроенных ключах
`rustfsadmin` / `rustfsadmin`, которые известны публично.

Контрольная проверка того же: открой консоль <http://127.0.0.1:9001> и попробуй войти как
`rustfsadmin` / `rustfsadmin`. Пускать не должно. Свои ключи из `.env` — должны.

### 5. Bucket для фотографий

В консоли <http://127.0.0.1:9001> создай bucket с именем `photos`. Пока вручную; на этапе 2
создание переедет в код API при старте.

### 6. Приложение

```bash
pnpm db:migrate
pnpm dev
```

`pnpm db:migrate` применяет миграции базы: на чистой базе включает расширения и создаёт таблицы,
при повторном запуске ничего не делает. `pnpm dev` поднимает API и фронт вместе.

Открой <http://localhost:5173> — на странице должно быть «API работает». Всё API доступно под
префиксом `/api`: проверка живости — `/api/health`, готовности базы и хранилища — `/api/ready`.

### 7. Остановка

```bash
docker compose down
```

Данные остаются в томах Docker. Чтобы удалить и их — `docker compose down -v`; это безвозвратно
стирает базу и все загруженные файлы.

## Порты

Все порты слушают только локальный адрес и наружу не публикуются.

| Адрес            | Что                                                  |
| ---------------- | ---------------------------------------------------- |
| `127.0.0.1:5433` | PostgreSQL (внутри контейнера — 5432)                |
| `127.0.0.1:9000` | S3 API хранилища                                     |
| `127.0.0.1:9001` | веб-консоль хранилища                                |
| `127.0.0.1:3000` | API на NestJS, всё под `/api`                        |
| `localhost:5173` | фронт на Vite в разработке; `/api` пересылает на API |

База слушает 5433, а не 5432, сознательно: 5432 на машине разработки обычно занят нативным
PostgreSQL из Homebrew.

## Переменные окружения

| Переменная          | Что                                     | Значение                       |
| ------------------- | --------------------------------------- | ------------------------------ |
| `POSTGRES_USER`     | пользователь базы                       | `jdm`                          |
| `POSTGRES_DB`       | имя базы                                | `jdm_garage`                   |
| `POSTGRES_PASSWORD` | пароль базы                             | секрет, задаётся локально      |
| `RUSTFS_ACCESS_KEY` | ключ доступа к хранилищу, аналог логина | `jdm-garage`                   |
| `RUSTFS_SECRET_KEY` | секретный ключ хранилища                | секрет, `openssl rand -hex 24` |

`POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` применяются **только при первой
инициализации тома**. Если поменять их в `.env` на уже созданной базе, изменения не подхватятся:
либо менять пользователя через SQL, либо пересоздавать том (`docker compose down -v`).

## Стек

TypeScript 6 (strict, ESM), NestJS 12, Drizzle ORM + PostgreSQL 18 + pgvector,
RustFS как S3-совместимое хранилище объектов,
React 19 + Vite + TanStack Router/Query + MUI, Vitest, Testing Library, Playwright, Testcontainers.

TypeScript намеренно зафиксирован на `~6.0.3`: в 7.x нет compiler API, из-за чего не работают
`nest build` и плагин Swagger.

## Если что-то не поднялось

**Порт занят** — `up` падает с `address already in use`. Кто держит порт:
`lsof -nP -iTCP:5433 -sTCP:LISTEN`. На macOS 5432 часто занят нативным PostgreSQL,
а 7000 — процессом AirPlay Receiver.

**Контейнер поднялся и сразу умер** — первым делом `docker compose logs <сервис>`.
Причина почти всегда написана там прямым текстом.

**`role "jdm" does not exist`** — том базы создан с другим значением `POSTGRES_USER`.
Переменные применяются только при первой инициализации: `docker compose down -v` и заново.

**Healthcheck зелёный, но ничего не работает** — так бывает. `pg_isready` проверяет, что сервер
отвечает, но не проверяет пароль; healthcheck хранилища проверяет HTTP-ответ, но не проверяет
ключи и наличие bucket. Зелёный статус — про живость, а не про правильность. Проверять надо то,
что должно сломаться.
