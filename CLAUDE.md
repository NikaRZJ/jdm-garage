# jdm-garage — CLAUDE.md

Учебный пет-проект: сайт-витрина импортёра JDM-автомобилей с админкой (MVP) и поиском на естественном языке (1.0). Цель — навыки, а не выручка. Источник правды по требованиям — документы в папке `~/Claude/Projects/jdm-garage/`, вне репозитория: PRD (`PRD-jdm-garage-2026-09-13.md`), контекст проекта (`jdm-garage-context.md`), план задач (`docs/tasks-stages-0-1.md`). Выжимка правил — ниже. Разработчик — frontend (React/TypeScript), бэкенд, база и инфраструктура для него зона роста: объясняй их через сравнения с фронтенд-практиками, не упрощая до потери точности.

## Стек и версии (проверены 14.09.2026, подробности — `docs/stack-versions-2026-09-14.md` в папке документов)

- Node 24 LTS, pnpm 12 (поле `packageManager` в корневом `package.json`), TypeScript `~6.0.x` — **не 7.x** (у 7.0 нет compiler API: ломаются `nest build` и Swagger-плагин), ESM во всех пакетах.
- `apps/api`: NestJS 12 (Express 5), zod 4 через Standard Schema (`@Body({ schema })`, глобальный `StandardSchemaValidationPipe`), `@nestjs/swagger` 12 + `zod-openapi`, Drizzle ORM 0.45.2 + drizzle-kit 0.31.10 с драйвером `pg` (node-postgres; переход на Drizzle 1.0 — пересмотр перед этапом 3, ADR-002), PostgreSQL 18 + pgvector 0.8, pino (`nestjs-pino`), `jose` + `argon2`, `@aws-sdk/client-s3` → RustFS, `sharp`, `@nestjs/schedule`.
- `apps/web`: React 19, Vite 8, TanStack Router (файловые маршруты, `validateSearch` через zod) + TanStack Query v5, MUI 9 с одной светлой темой, Material React Table для админки (совместимость с MUI 9 проверяется на этапе 2; запасной вариант — `@mui/x-data-grid`), react-hook-form + `@hookform/resolvers`; клиент API генерируется orval 8 из OpenAPI — руками не пишется.
- `packages/shared`: zod-схемы (фильтры, DTO, перечисления, статусы), сид справочника. `packages/config`: `tsconfig.base.json`, ESLint flat config, Prettier.
- Тесты: Vitest, Testing Library, MSW; интеграционные тесты API — `@nestjs/testing` + supertest + Testcontainers с реальным PostgreSQL (моки базы запрещены); e2e — Playwright.
- Не добавлять: `nestjs-zod`, Prisma, Passport-стратегии для JWT (auth пишется на `jose` осознанно), Redis/BullMQ (очередь — таблица в PostgreSQL с `FOR UPDATE SKIP LOCKED`), MinIO (репозиторий архивирован; заменён на RustFS), Tailwind. Новые зависимости — только по явной просьбе. Версия — старше суток: pnpm 12 не ставит более свежие (`minimumReleaseAge` = 1440 минут), дату публикации проверяй через `pnpm view <пакет> time`.

## Команды

Есть сейчас: `pnpm install` · `pnpm dev` (api + web; по отдельности — `pnpm --filter @jdm/api dev` и `pnpm --filter @jdm/web dev`) · `pnpm lint` · `pnpm format` / `pnpm format:check` · `pnpm typecheck` · `pnpm test` (unit) · `pnpm build` · `pnpm db:generate` / `pnpm db:migrate` · `docker compose up -d` (PostgreSQL + pgvector, RustFS).

Появятся на этапе 1, пока не вызывать: `pnpm db:seed`, `pnpm test:int` (интеграционные, Testcontainers), `pnpm e2e` (Playwright), `pnpm api:generate` (OpenAPI → клиент).

CI (`.github/workflows/ci.yml`) на каждый pull request в `master` запускает `lint`, `format:check`, `typecheck`, `test`, `build` — перед push прогоняй их локально.

## Правила

1. **Правило «руками».** Схему базы и миграции, схему аутентификации, устройство поиска, конфигурацию nginx и CI пишет разработчик сам. По этим темам: объясняй, задавай вопросы, предлагай варианты с последствиями, ревьюй — но не выдавай готовое решение целиком. Просьба «напиши X» по теме из этого списка правило не отменяет: отвечай, что это зона разработчика, и предложи разбор или проверку его варианта. Правило отменяется только явно, для конкретного случая: «в этот раз миграцию пишешь ты». Шаблонный код делай полностью: CRUD-эндпоинты, DTO и zod-схемы по описанию, формы, тесты по образцу, сидеры, конфиги линтера, скелеты модулей. Документы — ADR, заметки по задачам, README — пишет агент по итогам обсуждения; решения в них принимает разработчик.
   Границы (решения от 26.09): **auth** — ядро на `jose` (выдача, ротация, отзыв, семьи токенов, проверка access) пишет разработчик, обвязку (DTO, скелет модуля, тесты по образцу) — агент; **каталог** — фильтры, сортировка и пагинация — обычный CRUD-список, делает агент, разработчик ревьюит SQL; индексы и всё, на чём строится поиск (ADR-005), — разработчик; **инфраструктура этапа 3** — `Dockerfile` и prod-Compose пишет разработчик, скрипты бэкапа — агент, проверку восстановления делает разработчик.
2. **ADR.** Решение с альтернативами → `docs/adr/NNN-slug.md` (контекст, варианты, решение, последствия). Решение принимает разработчик в обсуждении — это и есть учебный момент; текст ADR по итогам обсуждения пишет агент, разработчик читает и правит. Если решение принимается без ADR — напомни. Заняты: 001 монорепозиторий, 002 ORM, 003 auth, 004 хранилище объектов, 005 поиск. Шаблон и порядок — скилл `/adr`.
3. **Тесты обязательны.** Unit для логики, интеграционные на реальном PostgreSQL для API, e2e-smoke для ключевых сценариев. Задача не готова, пока тесты не зелёные локально и в CI. Какие тесты и как писать — скилл `/tests-by-layer`.
4. **Безопасность.** Любой код про auth, файлы, SQL, LLM — сначала чек-лист PRD §8: argon2id; access-токен в памяти, refresh в httpOnly-cookie с ротацией и семьями токенов; CSRF-защита refresh (`Origin`/`Sec-Fetch-Site` + кастомный заголовок); ни `password_hash`, ни `token_hash` в ответах; только параметризованный SQL; тип файла по содержимому, перекодирование изображений; текст пользователя в промпте — только как данные.
5. **Терминология.** Машина = `Listing`, заявка = `Inquiry`, бронь = `Reservation`, справочник = `reference` (`Make`, `Model`, `Engine`), каталог = публичный список. Статусы — как в PRD §6.3: машина `draft / published / reserved / sold / archived`, бронь `active / expired / cancelled / completed`, заявка `new / in_progress / won / lost / spam`; переход вне таблицы — 409.
6. **Объём.** Пункт, который не ломает сценарий MVP и не кормит учебную цель, уходит в следующую версию. Не расширяй задачу без спроса, не добавляй «полезное рядом».
7. **Коммиты, ветки и PR.** Conventional Commits (`feat`, `fix`, `chore`, `docs`, `test`, `refactor`, `ci`); ветка называется по типу — `feat/…`, `docs/…`, `ci/…`. В `master` — только через pull request: правило на GitHub отклоняет прямой push и слияние без зелёной проверки `check`. Одна задача — один PR с коротким «что и почему»; слияние — squash, поэтому заголовок PR пишется как сообщение коммита по Conventional Commits. Коммит, push и PR агент делает только после явного «да» разработчика; сливает PR только разработчик — авто-слияние по зелёному CI не включать. В конце задачи — скилл `/finish-task`.
8. **Язык.** Документация, ADR, комментарии, тексты интерфейса — по-русски; код и идентификаторы — по-английски. Англицизмы в текстах только там, где нет нормального русского термина.
9. **Секреты.** Только в `.env` (в git не попадает); в `.env.example` — имена без значений. Содержимое `.env` не выводи и не читай целиком — только имена переменных. `docker compose config` печатает секреты открытым текстом — только с `--quiet`. Секрет, попавший в вывод или лог, считается скомпрометированным: скажи об этом, его меняют.
10. **Сначала объяснение, потом вопросы.** Если в разговоре появляется термин, которого у разработчика может не быть (миграция, расширение PostgreSQL, провайдер, триггер CI), — сначала объясни его с нуля, с аналогией из фронтенда, и только потом задавай наводящие вопросы. Вопросы на незнакомых словах не учат, а тормозят.
11. **Проверяй источник, а не пересказ.** Настройки образа — через `docker image inspect <образ>` и `docker run --rm <образ> --help`: документация и README расходятся с образом (так было с RustFS). Если библиотека ведёт себя не так, как написано в документации, — читай исходник в `node_modules` (так нашлось `ssl` у drizzle-kit). Проверка, которая не трогает проверяемое, ничего не доказывает: команда без подключения к базе не проверяет подключение.

## Скиллы

Лежат в `.claude/skills/`; вызываются командой или подключаются сами по описанию.

- `/adr` — записать решение с альтернативами в `docs/adr/`.
- `/tests-by-layer` — какие тесты писать и как: unit, компоненты фронта, интеграционные, e2e.
- `/finish-task` — закрыть задачу: проверки как в CI, заметка «что сделал и почему», тексты коммита и PR.

Скилл ревью миграций появится к задаче 1.2.

## Структура

`apps/api` · `apps/web` · `packages/shared` · `packages/config` · `compose.yaml` — локальная среда · `infra/` — nginx, prod-Compose и скрипты бэкапа (этап 3) · `docs/` (`adr/`, `runbook.md`, `notes/` — заметки по задачам и этапам, `perf/` — отчёты EXPLAIN, `sketches/`, `eval/` — с 1.0) · `.claude/skills/` — скиллы · `.github/workflows/ci.yml` — CI.

## Как ставить задачу агенту

Что сделать + где (пакет, модуль) + ограничения (стек, версии, «зависимостей не добавлять») + критерий готовности (команда, которая должна пройти). Ключевые решения уже в PRD и ADR; если нужного решения там нет — спроси, а не решай сам.
